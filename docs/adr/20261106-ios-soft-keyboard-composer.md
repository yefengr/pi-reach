# ADR-20261106: iOS 软键盘下的输入区：保持系统上推，按显示模式调整底部留白与阴影，发送后收起键盘

- 状态：已接受
- 日期：2026-11-06
- 后续调整：见[决策记录索引](20260518-closed-decisions.md#决策记录索引)。

## 背景

2026-11-06 输入区浮层（[ADR-20261105](20261105-floating-composer-and-notices.md)）的 iOS 真机验收中，点输入框弹出软键盘后有三处观感问题：

- 整页被系统上推，会话标题区移出屏幕，收起键盘后恢复。
- 主屏 PWA 的输入区与键盘之间约 34pt：其中 24px 是为 Home 指示条保留的底部留白（[ADR-20261028](20261028-ios-solid-status-bar.md)），其余约 10pt 是系统在辅助栏上方留出的空隙。
- 键盘上方有系统表单辅助栏（上下箭头与完成）。

2026-10-26 的 #139 曾尝试用脚本补偿（外壳跟随 visual viewport、锁文档高度、复位窗口滚动、收起过渡），补偿与系统上推互相干扰，标题区会先下坠再回位，因此改为完全交给浏览器，并接受标题区滑出屏幕。本次在 Safari 27 支持 `interactive-widget` 之后重新调研。

## 真机调研

2026-11-06 在 iPhone（Safari 27.2）上用独立探测页测量，探测页不接业务代码，按同一套几何读数比较各方案。

| 问题 | 结果 |
|---|---|
| `interactive-widget=resizes-content` 能否让外壳缩到键盘上沿 | 不能。WebKit 自 Safari 27.1 起支持该声明，但主屏 PWA 键盘弹出后 `position: fixed; inset: 0` 的盒仍为 812 高，可见区只剩 415，整页上推 397；外壳高度取 `100dvh`、`100lvh`、`100%` 或 `position: fixed` 四种结果相同 |
| 键盘上方的辅助栏能否去掉 | 不能。`textarea`、`input` 与 `contenteditable` 弹出键盘后可见区同为 415，辅助栏都存在；网页没有关闭接口 |
| 能否让系统不上推 | 能。点按时先聚焦屏幕顶部不可见的代理输入框，键盘弹出后把外壳缩到可见区高度，再把焦点交回真实输入框：标题区全程可见，页面上推为 0，焦点交回后键盘没有收起 |
| 系统上推的节奏 | 可见区读数一帧跳到终点；键盘比整页上推早 2–3 帧升起，弹出时键盘会短暂盖住输入区下半截（7–10 帧） |
| Safari 标签页 | 键盘弹出时浏览器在输入区与键盘之间显示地址栏，输入区下方本来就隔着浏览器的区域；同一页面两次弹出，输入区停的位置相差约 38pt，原因未查明 |
| 安卓 Chrome（主屏 PWA） | 执行 `resizes-content`：布局视口随键盘缩小，标题区留在顶部，输入区随外壳一帧贴到键盘上方，没有平移动画；收起时一帧恢复 |

## 决策

### 标题区保持系统上推

不采用代理聚焦。它需要拦截首次点按、在键盘打开后转移焦点，第一次点按无法定位光标，并且要与中文输入、听写、联想栏及输入区现有的焦点返回逐项重新验证；标题区留在屏幕上的收益不足以抵消这些风险。软键盘仍交给浏览器，不恢复脚本补偿。

### 主屏 PWA：软键盘到位后输入区停靠

触屏移动布局下软键盘到位后，输入区停靠：底部留白由 24 收为 0，卡片贴住键盘辅助栏，剩下系统自带的约 10pt 空隙；键盘收起或失焦即抬起。

- **判断软键盘**：脚本按可视窗口高度判断，有可编辑元素聚焦且可视高度比无键盘基准矮 120px 以上即为弹出，并且只在浏览器平移页面、布局视口（根元素 `clientHeight`）比可视窗口高出 120px 以上时标记；浏览器缩小布局视口时（安卓 Chrome）外壳已贴住键盘，不停靠。按实际行为而非系统或 UA 区分，WebKit 日后在主屏 PWA 缩小视口时自动不再停靠；只在根节点打 `data-soft-keyboard` 标记，不补偿外壳尺寸、不锁高度、不滚动。外接键盘不改变可视高度，不触发。
- **无键盘基准**：没有可编辑元素聚焦时键盘必然收起，此时的可视高度即基准，按显示模式与可视宽度分别记录并存入本地，每次读到都覆盖，过时的值随之纠正；键盘开着时旋转到新宽度也有基准可比。以宽度而非屏幕方向区分：键盘只改变高度，旋转与分屏必然改变宽度，且宽高在同一次尺寸变化中更新，不受方向事件先后顺序影响。失焦那一刻键盘尚未收起，不在焦点事件中记基准。
- **时机**：iOS 的可视高度、页面上推量与窗口滚动都在整页上推开始的那一帧一次变到终点，之后约 250ms 的上推动画由系统完成、网页拿不到进度或结束信号；三段录屏测得上推都是 250ms。因此键盘到位与停靠按两个独立动作编排：可视高度最后一次变化后等新增的 `keyboard-lag`（350ms，上推约 250ms 加约 100ms 停顿）再停靠。安卓若随键盘逐步缩小视口，「最后一次变化」即键盘到位的时刻。staging 真机录屏中 5 次弹出的上推均为 250ms，可视高度变化在上推开始后约 50ms 被检测到，上推结束到停靠开始的停顿为 133–167ms，停靠约 330ms，两步分明且节奏一致。
- **过渡**：停靠与抬起按侧栏的进入与离开取 `drawer`／`drawer-out`（360／280ms）与内容曲线，离开更快；贴底阴影与位移同一时长与曲线。

### 浏览器标签页：固定小留白

触屏浏览器标签页的输入区底部留白固定为 8，聚焦时不变、不过渡。

### 贴底阴影

卡片下方可见区域所剩无几时，`0 6px 20px` 投影会被截成一道硬边。新增 `--pwa-shadow-composer-docked`：保留接触层，投影上移 6px、内缩 6px（`0 -6px 20px -6px`），只向上方和两侧散开，卡片底边处浓度不足 1%。触屏浏览器标签页始终使用；主屏 PWA 在聚焦时随留白收起同步切换。深色模式本无 Composer 阴影，贴底阴影同为 `none`。

### 发送后收起键盘

触屏移动布局下发送成功后收起软键盘。按下发送仍不抢走输入框焦点；等本端发送过渡结束（footer 移除 `data-own-send`）再让输入框失焦，键盘下落不与气泡进入、输入区回缩叠在同一时刻。没有发送过渡时下一帧收起（附件需先上传时即属此类）；等待期间已开始输入下一条、发送失败而草稿保留或焦点已离开时保持现状。桌面布局不变，发送后焦点与键盘保持。

## 尝试过、没有保留的做法

| 做法 | 没有保留的原因 |
|---|---|
| 恢复脚本补偿 | #139 已证实与系统上推互相干扰，标题区会下坠再回位 |
| 改外壳高度基准（`dvh`／`lvh`／`%`／`fixed`） | 主屏 PWA 不执行 `resizes-content`，四种结果相同 |
| 上推基本结束后（延迟 280ms）再以 400ms 下沉 | 两段动作首尾相接，卡片随上推越过终点约 24pt 再落回，合成轨迹带回弹，与内容曲线「无回弹」不符；收起与恢复的时长也与「离开更快」相反 |
| 延迟 200ms，让下沉与上推后半段重叠 | 上推起始时机每次不同，同一段录屏三次弹出的过冲分别为 3.6、22.7、20.6pt，只有一次连成连贯动作 |
| 安卓也停靠 | 2026-11-06 安卓真机录屏：视口已缩小、输入区已贴住键盘，停靠在静止约 370ms 后又下沉约 22，成为多余的二次位移 |
| 聚焦后固定延迟 450ms 再下沉 | 测试设备上停顿稳定在 220–250ms，但以聚焦为起点，依赖聚焦到上推开始的间隔，换设备、换键盘或在安卓上没有依据；只看聚焦，外接键盘也会落座 |
| 按屏幕方向区分无键盘基准 | 方向事件与尺寸更新的先后顺序不定，方向先变时旧高度会记成新方向的基准；改按可视宽度区分 |
| 基准取见过的最大可视高度 | 记下偏高的值后无法回落（窗口调矮、系统升级、存下的旧值），会持续误判为键盘弹出；改为无聚焦时的读数直接覆盖 |
| 聚焦时立即收起留白 | 收起过渡恰在键盘升起时把卡片往键盘里拉，遮挡更深；改为延迟后，每次弹出完全看不到发送键的帧数从 5 降到 3–4 |
| 留白收为 0、保留原投影 | 投影被截成硬边（切口处亮度由 218 直接跳到 254） |
| 留 8–12px 间距、保留原投影 | 投影约 26pt 才完全消失，8pt 处仍有淡切口；12pt 时卡片离辅助栏约 22pt，失去贴住的效果 |
| 聚焦时只保留接触层阴影 | 切口消失，但卡片过平 |
| 浏览器标签页也在聚焦时收起留白 | 与 Safari 底部工具栏收成地址栏的动画叠加，输入区约 300ms 内来回位移 4–14pt；收起对卡片到键盘的距离几乎没有影响 |
| 浏览器标签页只在聚焦时换贴底阴影 | 未弹键盘时卡片下方 8 处也是浏览器工具栏，原投影同样被截断 |

## 后果与验证边界

- 自动化验证覆盖：触屏模拟下标签页与主屏 PWA 的留白、阴影和过渡时序，桌面与非触屏窄窗口不变，软键盘判断的基准、阈值、宽度区分、平移与缩小视口的区分与计时，发送后收起键盘的各个分支，以及贴底阴影 token 在浅色与深色下的取值。桌面 Chromium 无法模拟 iOS 软键盘，观感以 2026-11-06 主屏 PWA 与 Safari 标签页的 staging 真机录屏为准。
- 已知限制：横屏按桌面布局，不停靠；有一次从控制中心返回后首次聚焦时，iOS 没有上推页面，输入区在键盘弹出期间被完全遮挡，之后无法复现，原因未查明；停靠时机依赖 iOS 上推约 250ms 的系统动画时长；安卓只验证了主屏 PWA，Chrome 标签页与其他安卓浏览器未测；弹出瞬间键盘仍会短暂盖住输入区下半截；带附件的消息发送后立即收起键盘，不等待上传后的发送过渡。
- 重新评估条件：WebKit 让主屏 PWA 在键盘弹出时缩小布局视口或视口单位，或网页能提前得知键盘即将弹出时，重新评估标题区与外壳高度。

## 后续调整（2026-11-07）

staging 真机录屏中，键盘弹出后输入区停靠时，跟随最新的会话里消息列表随输入区一起下沉 24pt，未跟随时只有输入区移动，两种表现不一致。原因是停靠把输入区底部留白由 24 收为 0，输入区变矮，消息列表的底部留白随之变小，跟随最新时协调层把列表重新贴底，消息便与输入区同步下沉。

停靠改为把整个输入区（含上方渐隐与「最新」入口）以位移下移一个底部留白，留白本身不变：卡片仍贴住键盘辅助栏，输入区布局高度不变，消息列表的底部留白与滚动位置都不变，是否跟随最新，消息都保持原位。停靠时机、时长、曲线与贴底阴影不变；减少动态效果时位移与阴影仍一次到位。

停靠时机同时调整：不再在上推结束后等待，改为检测到软键盘即停靠，停靠与剩余的上推同时结束。原先等上推结束再单独停靠，输入区随页面升到终点上方 24pt、停顿后再落回，真机看来像回弹；收起时抬起与复位同一帧开始，叠加后整体单向运动，没有这个问题。弹出时网页无法得知上推何时开始，但检测时刻稳定：可视高度在上推开始的那一帧一次变到终点，staging 录屏中 5 次弹出都在上推开始后约 50ms 读到，因此以检测为起点、新增 `keyboard-dock`（200ms）取代 `keyboard-lag`，覆盖剩余约 200ms 的上推；停靠下移的 24pt 并入约 400pt 的上推。前文没有保留的做法均以聚焦为起点计时（聚焦即下沉、聚焦后延迟 200ms），与此不同。风险：键盘弹出初期会短暂盖住输入区下半截，停靠落在这段时间里，遮挡可能略深，以真机录屏验收。
