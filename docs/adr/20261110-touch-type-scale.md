# ADR-20261110: 触控设备独立字号基准与跟随系统文字大小

- 状态：已接受
- 日期：2026-11-10
- 覆盖：DESIGN「基础层」原单一 16px 字号基准、「Markdown 标题分两级且不大于会话标题」与页面标题行高 1.4

## 背景

字号原先只有一套基准（元数据 13、侧栏列表 14、正文 16、页面标题 24），同时用于桌面与手机。这组数值接近桌面习惯：iOS 的正文为 17、列表行为 17、分组脚注为 13，而 macOS 正文为 13，系统本身按平台区分。放到手机上，侧栏会话列表比 iOS 小 3px，设置说明、错误提示与输入区提示都落在 13px，中文笔画密时更吃力。

页面禁用了双指缩放，字号也不随系统设置变化，用户只能进设置页手动切档，默认值偏小的影响被放大。

Markdown 的 `#` 与 `##` 同为 18px，其余标题与正文同号；正文调大后，18px 的标题与正文几乎没有级差。

## 决策

1. 字号按主输入方式分两套基准，用 `pointer: coarse` 区分而不按宽度：桌面窄窗口不变，平板与手机一致。桌面基准不变；触控标准档为元数据 14、侧栏列表 16、正文 17、会话标题 18、页面标题 28，大档与特大档在此基础上顺延。带触屏的笔记本主输入仍是细指针，按桌面处理。
2. 触控标准档的代码保持 14px：390px 宽的屏幕每行约 42 个字符，再放大会增加横向滚动。
3. 字号偏好默认「跟随系统」。WebKit 以 `-apple-system-body` 实测系统正文字号，映射到已有三档（≥ 18px 大档，≥ 20px 特大档），不按连续倍数缩放，布局只需在三档下成立。小于默认的系统字号仍为标准档，保持「只放大不缩小」。应用回到前台时重新读取；用户选定档位后不再跟随。
4. 读不到系统字号的浏览器（含 Android Chrome 与桌面浏览器）偏好按标准档解析，设置页不显示「跟随系统」。Android 未接入：Chrome 的系统字号缩放由浏览器自身的文字放大机制处理，再叠加档位可能重复放大，留待真机核实后再定。
5. Markdown 标题分三级：新增一级、二级标题字号（桌面 20／18，触控 22／20），其余与正文同号加粗。一级标题可以大于会话标题：会话标题是导航栏文字，Markdown 标题属于正文内容的层级。
6. 页面标题与 Markdown 一、二级标题行高为 1.25（`--pwa-leading-title`），字号越大行高倍数越小；正文 1.65 与界面文字 1.4 不变。

## 未采纳

- iOS 正文约 1.29 倍的行高：面向拉丁文字，中文长文需要 1.6 以上。
- 12px 及以下的说明文字：保留 13px 下限。
- 500 等中间字重：Android 与 Windows 的中文字体通常没有对应字重，会退化为 400。
- 导航大标题随滚动收缩：属于原生导航行为，网页模拟成本高。

## 影响

- 触控设备上文字整体变大，每屏内容略少；已手动选过档位的用户保持原选择，但档位数值按触控基准变化。
- 未存储偏好的用户由标准档改为跟随系统，iOS 上系统文字大小调大过的设备会直接进入大档或特大档。
- `-apple-system-body` 在已安装到主屏幕的 PWA 中的表现需要真机验收；自动化测试以替换探针的方式覆盖映射与前台重读，触控基准以 Chromium 触控模拟覆盖。
- 当前规则以 [DESIGN「基础层」](../DESIGN.md#基础层)为准。
