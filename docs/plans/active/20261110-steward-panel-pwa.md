# 跨电脑任务管家与面板 PWA（独立项目预研）

> 状态：候选，未确定开发。本文调整原「管家面板 PWA」方案，将任务交接、主动通知和跨电脑续跑纳入同一预研；不代表已排期、已建仓库或获准实施。事项入口与当前项目级状态只在 [BACKLOG](../../BACKLOG.md) 维护。

## 1. 目标与使用场景

面向一个人在多台电脑、多个项目中同时使用 Pi 的工作方式，让用户只需查看一份「需要我处理」清单，就能知道哪些任务结束、如何验收，以及处理后能解锁什么。

| 当前问题 | 方案能力 | 用户可观察的结果 |
| --- | --- | --- |
| 需要逐台电脑、逐个会话检查任务是否结束 | 跨电脑任务汇总与主动通知 | 一处查看执行中、待决策、待验收及失败任务，重要变化主动送达 |
| 隔几天验收时已忘记背景与改动 | 持久任务卡与版本明确的交付说明 | 不翻聊天记录，也能理解原目标、交付内容、验证情况和验收步骤 |
| 没时间安排下一项工作，电脑与会话闲置 | 预排队列、依赖判断与自动续跑 | 已授权且条件满足的任务自动开始，需要用户判断的任务继续等待 |

优先减少用户检查和恢复上下文的成本，再提高执行连续性。机器空闲不是唯一调度指标；待验收积压、返工和费用也需要控制。

## 2. 产品边界与调整原因

这是独立项目，包含管家本体、每台电脑上的 worker 和面板 PWA。Pi Reach 继续提供当前在线 Pi 的远程控制与时间线阅读。常驻调度、队列持久化、任务验收和通知属于管家项目，不改变 Pi Reach 的[纯 Extension 边界](../../adr/20260914-pure-extension-runtime.md)或现有 Relay 职责。

原方案只讨论通过手机查看队列与审批，管家本体另见临时方案页，且明确不做主动通知。新的使用场景要求将队列、交付与调度一起设计，否则用户仍要主动打开面板检查，也无法在几天后直接验收。本文成为这份候选方案的完整入口，不再依赖临时讲解页理解核心流程。

本次调整：

- 管理对象由会话列表提升为持久任务；会话和执行尝试作为任务的关联记录。
- 将「待验收」与「已完成」分开，增加交付说明与验收闭环。
- 将主动通知纳入目标；首期通过服务端通知渠道实现，浏览器 Web Push 留待后续评估。
- 管家核心建议采用独立常驻进程，避免跟随某个长期 Pi 会话退出；Pi 可承担任务拆解与汇报辅助。
- 明确多电脑 worker、依赖、并行与积压控制，按交接汇总、通知、自动续跑的顺序验证价值。

首期范围限于个人与 Pi。不做多用户团队协作、通用工具调用审批平台、电脑远程唤醒、浏览器后台可靠执行、面板内完整聊天时间线或日志与 diff 查看器。面板提供交付摘要和证据入口，详细代码审查仍使用适合的工具。

## 3. 日常工作流程

1. 用户或管家辅助生成任务卡，写明背景、目标、边界、预期结果、验收方式、依赖和允许执行的动作。尚需澄清的卡片留在草稿，不自动执行。
2. 用户将范围明确的任务加入队列，也可登记正在运行的现有 Pi 会话。所有登记与状态变更走同一命令服务。
3. worker 执行队列任务，回传运行状态、实际验证结果和交付材料。任务达到交付条件后进入待验收，管家发送通知。
4. 用户有空时打开「需要我处理」，直接按交付说明验收。通过后标记已完成；不通过则记录反馈，形成新的执行尝试。
5. 调度器继续安排满足依赖和授权条件的任务。独立任务可在前一项待验收期间运行；需要用户确认前项结果的任务继续等待。

支持两种接入方式，能力分别标明：

| 方式 | 用途 | 自动化边界 |
| --- | --- | --- |
| 登记现有会话 | 把已经分散运行的任务纳入统一清单，关联电脑、项目与会话，并补充交付说明 | 首期支持手动登记和明确提交状态／交付；实时事件接入需另验证，不能仅凭登记就接管进程、恢复历史或保证结束通知 |
| 管家派发任务 | 由 worker 在明确的目录和授权下启动、记录并管理一次执行 | 可自动汇报、核对交付条件和续跑；进程控制仅作用于自身管理的执行 |

不要求把所有现有会话重开，也不假设能自动发现所有电脑上的历史任务。希望获得可靠自动结束通知的任务，必须有可验证的事件或 worker 回传路径。

## 4. 任务、执行与在线状态

任务拥有稳定 `task_id`，独立于电脑名称、目录、Pi endpoint 和 session。返修或重试创建新的 `attempt_id`；任务卡版本、执行输入、交付版本与验收记录分别保留关联。

| 任务状态 | 含义 | 离开条件 |
| --- | --- | --- |
| 草稿 | 目标、授权或输入尚未准备好 | 用户确认任务卡后进入待开始 |
| 待开始 | 可以排队，尚未开始执行 | 调度条件满足且执行已确认开始，或明确登记现有执行 |
| 执行中 | 存在已确认正在执行或验证交付的尝试 | 形成交付、需要用户输入，或明确失败／停止 |
| 待决策 | 存在具体问题、授权请求或交付材料缺口 | 用户回答并确认后恢复或终止 |
| 待验收 | 交付说明齐备，约定的自动验证已满足或已明确约定人工确认范围 | 用户确认通过，或提交返修反馈 |
| 已完成 | 用户确认指定交付版本通过验收 | 后续新需求另建任务，不改写原验收事实 |
| 失败 | 本次执行明确失败，需要处理或重试 | 用户或预授权策略允许新的执行尝试 |
| 已取消 | 用户终止本次任务 | 需要恢复工作时显式重新排队 |

归档是清单显示属性，不等于验收通过；待开始任务另有「等依赖、机器离线、额度不足、积压限流」等调度原因，不把它们混成执行失败。

在线状态、心跳、进程状态与任务状态分别保存。断线只更新连接与执行可确认性，保留最后已确认的任务事实和时间；执行去向不明时标记「待核对」，阻止该任务的重新派发，不能把它当作完成或自动重试。

Pi Reach 的 `working` 与 `run_end` 可以作为运行信号。`run_end` 表示一轮运行正常结束、中断或错误；其中的 `complete` 不证明用户目标已达成。进入待验收还需要匹配本次尝试的交付材料和约定验证；约定检查失败进入失败，明确的输入或交付缺口进入待决策，不以模型自称完成替代核对。

## 5. 任务卡与可恢复上下文

任务卡既供用户回忆，也供新会话接手。创建时以自然语言为主，不要求用户填写大量技术字段；管家可根据描述生成草稿，但会影响范围、授权或依赖的缺口应在入队前确认。

| 内容 | 需要记录什么 |
| --- | --- |
| 目标与背景 | 当初的问题、为什么要做、预期可观察的行为 |
| 范围与约束 | 项目、允许改动范围、不应触碰的内容、相关项目规则 |
| 参考与决定 | 必要文档、已确认决定、仍需回答的问题；引用现有真源而非复制全文 |
| 交付与验证 | 预期产物、适合该任务的自动检查、人工验收步骤与通过条件 |
| 授权 | 可自行执行的动作、需要另行确认的动作，以及适用的费用和并行限制 |
| 依赖与机器 | 前置任务和解锁条件、项目可用的电脑与工作区要求 |
| 执行与版本 | 每次尝试的输入版本、工作目录、基线、关联会话和结果位置 |

不把整段聊天作为唯一上下文。对探索或调查任务，验收条件可以是明确问题得到有证据的回答及未知项说明，不强行套用代码测试。

同一项目已有路线图、Issue 或方案时保留链接和同步责任，不在管家里手工维护一份相互竞争的项目状态表。管家持有任务执行与验收事实，不自动改写仓库长期文档中的事项状态。

## 6. 待验收交付说明

任务进入待验收前，形成一份绑定本次交付版本的说明；验收记录必须指向该版本。返修后生成新版本，保留此前反馈，不沿用旧的验收通过状态。

| 部分 | 用户需要看到的内容 |
| --- | --- |
| 当初要做什么 | 原问题、目标和确认过的范围 |
| 现在交付什么 | 主要变化、产物和实际效果；未覆盖范围单列 |
| 已验证什么 | 实际执行的检查、结果和证据位置；人工检查与未执行项明确区分 |
| 如何验收 | 打开哪个入口、做哪些操作、应该看到什么、预计需要多少时间 |
| 风险与决策 | 已知问题、需要用户选择的具体问题及其影响 |
| 下一步 | 通过或返修后分别解锁哪些任务 |
| 版本与追溯 | 基线及交付标识、对应工作区或提交、报告版本、关联执行尝试 |

代码任务尚未提交时，可用独立工作区和变更快照标识交付，不为获得提交号擅自提交。预览入口应注明适用版本和有效性；过期、离线或已被后续部署覆盖时必须可见，不能让用户对着新版本验收旧任务。

模型可以组织说明，验证结果和版本标识由实际记录提供。缺失证据写明未知或未验证。报告中保留原执行结果的追溯入口，不将自动摘要作为测试通过的证明。

交付与必要工作区在验收完成前保留。清理按独立策略执行，不能因任务进程退出或后项启动就删除待验收产物。

## 7. 自动续跑与依赖

自动续跑消费用户已确认的队列，不由模型无限生成新的开发工作。新建议先进入草稿；授权和依赖不足时停止该项，不反复调用模型询问同一个问题。

依赖至少区分两种条件：

- **交付就绪**：前项已形成指定版本的产物，且约定自动验证满足；只有显式允许消费该产物的后项才能解锁。返修使该产物失效时，暂停尚未开始的后项，已开始的后项标记需要复核。
- **验收通过**：前项指定交付版本得到用户确认后才解锁。需要产品方向或交互效果确认的后项使用此条件。

没有依赖的任务可独立运行。已知有前置任务但解锁条件未明确时，默认等待前项验收；前置关系本身不明确时，先澄清再入队，不根据「看起来相关」自动建立可续跑关系；拒绝循环依赖。

例如 A 修复界面问题并待验收，B 排查另一个独立构建问题，C 基于 A 的最终交互继续开发。B 在工作区隔离且额度允许时可以运行，C 等待 A 验收通过。A 验收失败后进入返修，不能仍将 C 视为前提已满足。

调度前同时检查：

1. 任务卡已确认、授权有效、依赖满足，目标机器在线且具有所需项目与执行环境。
2. 全局和单机并行位、费用限制及待验收积压允许继续开始任务。
3. 工作区、共享文件、预览和部署资源没有所有权冲突。同仓库写任务使用独立分支／worktree；涉及共享配置、集成分支或同一 staging 时串行协调。
4. 该任务没有未核对或仍在停止过程中的旧尝试。

待验收设置可调上限，试用时可先设为三项，观察后调整。达到上限停止新增需要验收的工作，只允许此前明确授权、不会继续扩大积压的工作；不能以保持机器忙碌为由绕过限制。

费用采用每日限额与全局／单机并行上限。每次尝试记录实际花费，缺失时显示未知；达到限额停止新派发，运行中超额的停止策略与统计延迟需在实施前明确，不承诺仅靠事后记账实现硬性封顶。

## 8. 管家本体与多电脑架构

建议拓扑如下，其中两类控制连接都需要先通过可行性验证：

```text
面板 PWA（控制方 owner）
    ↕ 现有 Relay：认证、ACL、实时路由
管家网关（独立 device／endpoint）
    ↕ 统一命令服务
管家协调器 + 持久任务库 + 通知发件箱
    ↕ 协调器以另一 owner 身份，经 Relay 连接已配对 worker
各电脑 worker（各自独立 device／endpoint）
    ↕ 本机受管执行
独立工作区 + Pi 执行尝试 + 交付产物
```

协调器、网关与任务库首期可以在同一台常用电脑或常驻主机运行，本机也可运行 worker。具体部署机器待确认；协调器下线时不会有新派发，现有 worker 的回传留待恢复后核对。

| 组件 | 职责 |
| --- | --- |
| 命令服务与持久任务库 | 唯一任务写入口；校验状态、授权、版本与幂等请求，原子保存状态变更和通知事件 |
| 确定性的调度器 | 按依赖、资源、积压和授权派发任务，不依赖一个长期模型会话维持状态 |
| 每机 worker | 维护项目映射、准备工作区、管理自身启动的 Pi、回传心跳与结果，并保留待回传记录 |
| 可选的管家 Pi | 辅助拆任务、解释阻塞、整理交付，所有建议与写操作走同一命令服务 |
| 通知适配器 | 从持久发件箱发送提醒，记录送达尝试、重试与失败 |
| 面板 PWA | 跨机器任务清单、交付阅读、决策与验收入口 |

任务数据只有协调器一份权威写模型。建议使用支持事务的本地持久存储，具体选型在实施前确定；旧的队列 YAML 可作导入／导出格式，不让多个电脑通过同步目录并发改同一组文件。CLI 是命令服务的客户端，面板、模型与 worker 均不绕过它直接改状态。

管家常驻能力由独立项目实现，不通过 Pi Reach 的旧 `daemon` metadata 或普通 Pi endpoint 冒充。面板网关身份、协调器控制身份及 worker 身份与 Pi Reach 配对分开管理；可见性由 owner 订阅与设备 ACL 决定，不能仅靠更换 device 名称保证隔离。

## 9. 执行、重启与停止

每次派发携带任务卡版本、`attempt_id` 和领取凭据，worker 持久去重后才确认接收。同一尝试的网络重发返回已有结果，不再次启动；过期尝试的迟到回传不能覆盖当前尝试。

worker 持续回报心跳，但心跳失效只说明暂时无法确认状态。协调器重启或失联后，先核对 worker 的尝试记录、进程与产物；没有证据证明旧执行已停止时，不向其他电脑重新派发同一任务。不能用领取超时替代停止确认。

取消请求先进入「停止中」的执行状态，收到 worker 停止确认后才将任务标记已取消。停止过程保留已有改动；用户取消不自动删除工作区、回滚代码或撤销已发生的外部动作。非受管会话只提供登记与结果记录，不宣称能可靠停止。

执行入口优先验证 Pi 的非交互模式，由 worker 管理独立尝试；需要持续会话控制时再比较 RPC／SDK。启动、事件、退出和恢复的行为以实施时安装版本的文档与实测为准，不把某个结束事件或退出码直接等同于任务验收条件。

任务授权按明确动作管理。批准推送、发布或其他外部操作时，应绑定任务、交付版本、动作和目标；任务变更后不能复用旧批准。首期不承诺靠命令文本匹配实现通用 shell 审批或安全沙箱。

## 10. 主动通知

通知由协调器后台发送，不依赖面板保持前台、手机锁屏连接或用户手动刷新。首期选择一种用户日常会看的通知渠道，并通过适配器保留替换能力；渠道及凭据存储方式在实施前确认，实际发送测试通知前需明确授权、接收方和内容。

| 事件 | 提醒方式 | 最少内容 |
| --- | --- | --- |
| 待决策、执行失败、执行待核对 | 及时提醒同一问题，避免反复刷屏 | 任务、电脑、具体问题、受阻工作和处理入口 |
| 新交付进入待验收 | 短时间多项完成时合并提醒 | 任务目标、交付摘要、预计验收时间和入口 |
| 到约定时间仍有积压 | 可配置汇总 | 等待最久的任务、阻塞关系和建议处理顺序 |
| 普通执行进展 | 默认留在面板 | 当前状态与更新时间 |

任务状态变化与通知发件箱在同一事务中记录。发送失败保留重试记录，面板显示通知故障；重复发送使用稳定事件标识合并。通知渠道确认接收不等于用户已读、已处理或验收通过。

通知仅带必要摘要与面板任务定位链接，默认不传完整报告、代码、命令输出或凭据。链接只是定位入口，仍需已配对身份访问，不是公开分享链接。Web Push 是可选后续渠道，其服务端与浏览器兼容验证属于管家项目，不要求 Pi Reach 或 Relay 增加推送职责。

## 11. 面板与验收交互

手机用于快速处理，桌面用于集中安排与批量阅读，两端访问同一任务库。默认页优先显示「需要我处理」，其下区分待决策、待验收与失败／待核对；执行中、待开始和已完成作为其他视图。电脑在线数、当前并行和费用在汇总区显示，不占据任务正文。

任务详情先呈现目标和交付说明，再呈现必要追溯信息。提供以下操作：

- 待决策：回答具体问题，或批准／拒绝明确动作。
- 待验收：确认当前交付通过，或附反馈要求返修。
- 待开始／执行中：调整队列、暂停新派发、请求停止受管尝试。
- 失败／待核对：查看原因，完成核对后重新排队，或取消。

批量操作只覆盖用户明确选中的任务与交付版本，返回逐项结果；禁止把一批待验收默认全部通过。并发修改时提示刷新，不将旧页面上的点击应用到新版本。

详细会话仍通过 Pi Reach 查看。首期可以打开 Pi Reach 并提示目标机器和会话；任务深链与历史恢复能力尚未验证，不承诺一键直达或恢复已结束的 Pi。面板交付内容不依赖在线会话存在；本机文件路径不能冒充手机可访问的证据链接。

数据策略统一为：已加载快照可留在当前页面内存中，断线时明确标记最后同步时间并禁用写操作；不将任务队列持久缓存到 IndexedDB。离线重开只显示连接说明。每次回到前台先拉取权威快照，再恢复操作，不依赖后台持续同步。

## 12. 管家业务协议

复用现有外层认证与路由，`steward_*` 业务使用独立版本和严格 schema，不冒充 Pi Reach 的会话帧，也不修改现有会话协议语义。以下是需求契约，完整字段和 schema 在可行性验证后冻结。

| 方向 | 消息范围 | 关键要求 |
| --- | --- | --- |
| 面板 → 管家 | 任务清单／详情、任务创建与修改、回答问题、验收／返修、明确动作批准、停止／重试／归档、订阅 | 写操作含请求 ID、预期任务版本；验收与批准另绑定交付或动作版本 |
| 管家 → 面板 | 权威快照、任务详情、逐项操作回执、变更事件、错误与能力信息 | 状态、交付、在线情况和调度原因分字段传输 |
| 管家 → worker | 能力查询、派发、状态核对、停止请求 | 绑定机器、任务卡版本、执行尝试及领取凭据，持久去重 |
| worker → 管家 | 接收回执、心跳、问题、验证结果、交付、停止确认、失败与恢复记录 | 标明尝试与事件序号，重复或迟到回传不覆盖当前状态 |

协议需要覆盖：

1. **服务端权威与恢复**：快照带数据代次和单调修订号；增量历史缺失或代次变化时重新取全量，不跨恢复点误用旧修订号。
2. **持久幂等与冲突**：请求去重记录跨进程重启保留，同 ID 不同内容拒绝；版本冲突不静默覆盖。worker 确认已持久接收后才能视为派发成功。
3. **先持久后回执**：状态、交付引用和待通知事件落盘后才返回成功；协调器不可用时 worker 保留待回传结果。
4. **边界与能力**：未知业务版本、方向或字段明确拒绝；可选能力显式协商。详情与交付分页／限量传输，不把完整日志或大文件塞进帧体。
5. **授权主体**：使用 Relay 注入的控制方身份匹配 ACL，不接受 payload 自报身份。面板和 worker 的业务权限分别校验。

## 13. 连接复用与部署前提

优先复用 Pi Reach 已有能力，先验证边界后迁移所需代码：

| 可借鉴或迁移的能力 | 当前来源 | 需要核对的边界 |
| --- | --- | --- |
| 外层握手、认证、路由类型与编解码 | `packages/protocol/outer` | 当前包标记为 private，不能假设可直接安装公开发布版 |
| owner 连接、配对与浏览器身份存储 | `pwa/src/lib/pi-reach/`、`pwa/src/lib/pwa/` | 分离会话依赖；协调器在 Node 中使用 owner 连接的可行性另验证 |
| device 连接、重连、存活检测 | `pi-extension/src/transport/` | 脱离 Pi Extension 生命周期运行需要适配，不能原样视为独立 worker |
| 身份、钥匙串与配对流程 | `pi-extension/src/pairing/` | 独立存储命名空间，分别验证管家网关和 worker 的撤销 |
| PWA 安装、Service Worker 与更新提示 | `pwa/src/app/sw.ts` 及相关配置和组件 | 移除 Pi Reach 会话业务，检查新应用作用域和更新流程 |

建议独立仓库和发布流程，首期定向迁移必要连接代码；不为本候选抽取新公共包或修改 Pi Reach 的发布策略。若选择包依赖，需另行确定分发方式与授权，不能沿用原方案中未经验证的「发布版依赖」。

PWA 仍可作为 HTTPS 静态站点部署，但完整系统还需要常驻协调器、持久任务库、通知适配器和各机 worker，不能把静态面板的部署成本当作整套系统成本。两类连接复用现有 Relay 的可行性要经过验证；发现缺口先回到方案评估，不默认改 Relay。

## 14. 身份、隐私与数据保留

面板与管家网关配对，协调器分别与各 worker 配对。密钥、ACL 和通知凭据持久保存在对应端的独立命名空间，撤销入口必须在被控端可用。撤销控制方后停止接受其新请求；对已在执行的任务如何处置需明确策略，不承诺撤销等于回滚或即时杀死所有进程。

Relay 是完全受信的一方，TLS 不提供应用层端到端加密；经 Relay 传输的任务、交付与控制消息对运营方可见，也继承其可冒充控制方的信任边界。敏感场景使用自托管 Relay。通知渠道引入另一接收方，发送内容按最少必要摘要控制。

任务与报告不写凭据，模型凭证留在执行电脑，通知凭据留在通知适配器配置中。面板不提供公开报告链接；外部证据链接另行标明访问要求。自动摘要和日志展示仍要检查敏感内容，不能仅靠任务描述中的使用约定保证安全。

持久保存任务版本、执行结果、交付和验收事实；日志与工作区按明确保留策略处理。任务库需要备份与恢复验证，恢复后更换数据代次并核对未终结尝试，不能把备份中的旧领取状态直接用于新派发。

## 15. 分阶段与验收门槛

| 阶段 | 交付范围 | 验收门槛 |
| --- | --- | --- |
| 0：验证关键链路 | 最小协调器持久任务、面板配对与读写；单机 worker 执行并回传，再验证第二台电脑；通知测试使用显式授权渠道 | 重启后任务仍在，重复请求不重复执行，两类连接可用；确认现有会话登记和 Pi 执行入口的实际能力 |
| 1：任务交接与汇总 | 现有任务手动登记、受管任务汇报、跨机清单、交付说明、验收／返修和版本保留 | 隔几天无需翻会话即可验收；清楚区分执行结束、待验收、已完成和待核对；首期由用户手动选择受管任务启动 |
| 2：主动通知 | 一种通知渠道、持久发件箱、重要事件提醒、合并和可选积压汇总 | 手机未打开面板时仍能收到提醒；发送失败可见并可重试；重复提醒不重复改变任务状态 |
| 3：自动续跑 | 预排队列、两类依赖、机器分配、工作区隔离、积压／费用／并行限制和停止核对 | 独立任务在前项待验收时继续，需要验收的后项等待；断线与重启不导致重复派发，返修不会沿用旧版本的解锁结论 |
| 4：日常试用与加固 | 安装体验、备份恢复、真实多电脑与移动端试用，集中修复流程缺口 | 相比逐台检查，减少手动检查、上下文恢复和无意空档，同时不持续扩大验收积压 |

阶段 0 是技术可行性验证，后续先验证交付与汇总是否有用，再投资通知和自动调度。PWA 安装能力可以按试用需要加入，不以 UI 完整度替代任务闭环验收。

试用观察手动检查次数、发现阻塞的等待时间、打开交付到能够验收所需时间、积压数量与等待时长、可执行任务等待派发的时间、重复执行和通知失败。具体统计口径与目标值随试用确定，不以会话在线时长或机器持续满载作为成功证明。

## 16. 失效模式

| 故障 | 可见表现 | 处理边界 |
| --- | --- | --- |
| 协调器退出或主机休眠 | 面板断线，新派发与通知暂停 | 常驻服务恢复后加载持久状态，先核对 worker；已有任务不能凭重启自动重跑 |
| worker 断线或电脑休眠 | 最后心跳过期，受影响尝试待核对 | 保留任务事实和工作区，确认旧进程终态后才允许重派 |
| Pi 正常退出但缺少交付或检查失败 | 明确显示材料缺口或失败 | 补齐材料／返修，不直接归入待验收或已完成 |
| 现有会话结束但未接入事件回传 | 登记信息没有新的可确认状态 | 提醒需要手动核对，不制造自动完成通知 |
| 通知渠道不可达 | 任务仍正常流转，通知发送失败 | 持久重试并在面板提示；通知失败不丢失待办 |
| 手机后台挂起或 Relay 重启 | 面板失联或重新握手 | 回前台拉权威快照；离线数据只读，不缓存写操作等待自动重放 |
| 验收入口过期或被覆盖 | 交付仍在，但预览标记不可用或版本不符 | 恢复指定版本入口，或显式提交新版交付后再验收 |
| 旧页面提交验收、重复点击或迟到回执 | 版本冲突或返回已有操作结果 | 不重复执行，不把旧确认应用到新交付 |
