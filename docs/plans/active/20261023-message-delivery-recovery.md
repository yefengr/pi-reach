# 消息投递与异常恢复方案

- 日期：2026-10-23
- 用途：明确文字、附件、排队消息的发送呈现、确认与恢复规则，作为后续实施依据；不是当前实现说明。
- 授权边界：本轮完成实现与验证，不包含提交、推送或发布。事项状态见 [ROADMAP](../../ROADMAP.md)；本文不维护第二份项目级状态。
- 核对基线：`0848bae`。当前事实以 [ARCHITECTURE](../../ARCHITECTURE.md)、[DESIGN](../../DESIGN.md)、[会话协议](../../reference/protocol/protocol-v2.md)和代码为准。

## 1. 目标与取舍

用户已确认的体验是：消息正常发送时立即显示普通气泡，不显示“发送中”或“发送成功”；明确失败才显示原因及适用的重试图标；无法确定是否送达时允许显示“尚未确认”。

“默认成功”只指乐观呈现，不代表提前生成正式历史或跳过内部确认。附件上传、排队管理和正式历史确认都要重新梳理，但不重写上传协议、Pi 调度队列或时间线存储。

本方案选择在现有模块中统一消息投递规则，增加一个只读状态查询请求，不引入通用状态机框架或第二套发送队列。

### 本轮不做

- 不增加 IndexedDB 投递表、离线自动发送、后台补发或跨设备恢复。上一轮讨论的本地持久投递记录不纳入本方案。
- 不持久化浏览器 File 原件；不承诺刷新页面、关闭页面或 Pi 重启后还能恢复未确认消息。
- 不增加“强制重发”按钮及确认流程。无法证明未执行时，只核对状态或保留内容供用户复制，不由系统重新投递。
- 不新增 Relay 存储、HTTP 服务、第三方依赖、通用任务管理器或无限轮询。
- 不重构视口协调器、Working 提示或模型运行状态；仅删除普通发送状态行及其专用布局补偿，保留现有气泡身份和跟随规则。
- 不为旧端维护两套投递逻辑、能力协商矩阵或“查询失败就改用发送”的降级路径。

这些限制意味着：本方案保证的是当前页面、有效会话内的可靠识别与恢复，不承诺跨进程的恰好一次执行。

## 3. 用户看到的状态

| 情况 | 呈现与操作 |
| --- | --- |
| 本地已建立消息，正在等接收／启动回执 | 普通气泡，无“发送中”、对勾或常驻占位 |
| Pi 已开始处理，正式记录尚未合入 | 原气泡继续显示，不把历史补齐耗时算成发送失败 |
| Pi 已确认排队 | 使用现有排队区和允许的插入／撤回操作，不重复出现异常气泡 |
| 确定没有提交出去，或远端在投递前明确拒绝 | 气泡附近显示短原因；可直接重试时显示 `RefreshCw` 图标，否则说明需要修改内容或恢复连接 |
| 投递结果无法确定 | 中性“尚未确认”与 `RefreshCw` 核对图标；离线时说明连接恢复后可核对，不提供无效点击 |
| 收到正式记录 | 合并原气泡，移除异常；不新增一条相同正文、不重播入场动画 |
| 仅本地历史保存失败 | 使用历史保存错误反馈，不更改消息投递结论、不允许因此重发 |

失败与未知都留在对应消息附近，不再叠加同一原因的全局错误。图标保留 44px 点击区、`aria-label` 和 `title`，分别命名为“重试发送”和“核对状态”，不能因为图形相同就共用含糊的“重试”语义。中英文文案同步维护。

普通路径不渲染投递状态行，也不保留它的空白。异常操作按正常文档流布局，不覆盖正文；状态交接保持气泡、阅读锚点和用户回看意图。

## 4. 三条业务路径的调整

### 4.1 文字与附件共用消息提交

在 PWA 现有业务层收敛一个消息提交入口，由 `PwaApp` 的文字发送和附件就绪回调共同调用；`TimelineRuntime` 仍是投递状态唯一所有者。是否抽出一个局部模块由实现后的职责决定，不按文件行数另造框架。

交接结果明确为“未接管”或“已接管”，不再让一个布尔值同时表示草稿归属、网络发送和远端确认：

1. 校验失败、容量不足或目标失效，尚未建立消息时，返回未接管：保留草稿，错误留在输入区，不产生第二份失败气泡。
2. 建立消息后返回已接管：固定正文、附件描述与逻辑消息 ID，由 runtime 负责后续状态；草稿按既有版本保护清理。
3. 已接管后若本地 transport 明确未接受发送，原消息进入失败状态，按原因决定是否可重试，不能同时把同一份内容当作仍待提交的附件草稿。
4. transport 接受只证明本地提交成功，不证明 Pi 收到。发送跟随和尺寸过渡仍只在 transport 接受后激活；失败不制造成功发送动效，重试不重播气泡入场。

“已接管但未发送”的失败可以在原气泡重试，不因失败重复创建消息。任何迟到回调都不能清掉用户后续编辑的草稿。

### 4.2 附件只负责准备文件

保留逐文件上传进度、取消、失败重试，以及同目标、同租约内的恢复能力。全部保留文件就绪后交给统一消息提交入口；上传完成不是消息投递成功。

交接前由 `AttachmentComposer` 持有文件和上传任务，交接后由 runtime 持有消息及其附件描述。远端可能已交给 Pi 的原件继续遵守现有 retain 保护，不因气泡未知、用户离线或本地清理而删除。

重试消息前校验原目标和附件租约：附件仍有效时复用原 ID，不重新上传；租约失效时不盲发旧 ID，提示重新选择文件。只有明确失败的消息可以通过受控的“返回草稿”交还内容；未知投递不能伪装成撤销成功。跨刷新恢复原件不在本轮范围。

### 4.3 排队与正式历史不再代判发送结果

- 权威队列快照仍决定是否排队、是否在途以及是否可操作。`cancelable` 表示权限，不能代替真实阶段。
- 排队等待不套用普通投递确认超时；已进入在途但迟迟没有启动确认，才需要核对。
- 项目从队列消失不是成功或失败的充分证据。先接收启动／正式事件／取消回执；撤回成功时 Extension 先回复定向 `cancelled`，再发队列快照。证据不足时进入核对，而非重新发送。
- 只有服务端确认尚未投递的队列项已取消，才回填草稿；插入未确认不能转成普通消息重试。插入已调用 SDK 后，即使同步抛错也必须退出可操作队列，保留有界关联等待启动／正式事件，不能重新入队、再次插入或当作取消成功；同一次调用内已取得的启动／提交证据不能回退。
- 正式事件与投递回执允许乱序。通过请求 ID 与 `message_id` 关联，不比较正文猜测身份；两条相同文字仍是两条独立消息。
- Pi 已确认接收／启动后，历史同步和 IndexedDB 保存是独立问题。正式记录到来时原位合并，未取得正式记录前不伪造一条历史事件。

## 5. “尚未确认”的恢复流程

### 何时出现

仅在缺少必要投递证据时出现：未获明确受理便断线、投递确认超时、SDK 投递结果不明，或排队项离开队列后仍无法解释其去向。模型思考慢、运行时间长、回复尚未结束都不是触发条件。

普通提交和在途启动的确认等待先采用与现有投递启动超时一致的 30 秒，使用具名常量和可控时钟测试；真正排队不启动该计时。断线立即结束当前等待并保留未知，不依靠后台定时器证明失败。

### 如何核对

1. 同一目标恢复握手并取得完整队列快照后，对当前仍未知的本端消息各发一次只读查询；已有正式记录的消息无需查询。
2. 在线期间达到确认超时，也进行一次查询。查询无结果后保留“尚未确认”，不自动循环。
3. 用户点击“核对状态”只触发一次查询；同一消息同时最多一个查询，等待期间禁用连点。等待超时只结束按钮等待，查询关联仍在短期有界预算内保留；迟到的有效状态仍可合并原消息。关联的当前上限见[会话协议](../../reference/protocol/protocol-v2.md#消息投递确认)。新查询、新发送尝试、新队列操作或连接／目标失效后，旧查询不得结清新操作。
4. 恢复的是另一个 runtime／会话、原 Pi 已退出或发生真实分支替换时，不把旧消息转投新目标，也不通过旧通道核对；说明原目标不可用，保留仍在本页内的内容供复制。

下表以消息仍缺少相应投递证据为前提。查询等待期间若收到新的回执或正式记录，按[状态合并规则](#按投递证据合并状态)处理，不能被较早查询的结果回退。

| 查询结果 | PWA 处理 |
| --- | --- |
| 已接收或仍在排队 | 撤销未知提示，按真实阶段显示；排队资格仍由完整快照决定 |
| 已启动或已提交 | 关联 `message_id`，撤销未知提示，复用现有历史补齐与合并 |
| 明确拒绝且确认未进入投递 | 转为失败，按结构化原因决定是否可重试 |
| 已确认取消 | 按原队列取消关系结清；只有本端对应的撤回请求才回填草稿，且仅一次 |
| 结果未知、记录不存在或查询失败 | 保持“尚未确认”，不自动发送、不猜成失败 |

查询收到“已接收”不能重置成可无限延长的正常等待：若仍缺少后续阶段证据，完成一次有界确认等待后继续显示尚未确认，等待新证据或用户操作，不自动再查。

本轮不提供“强制重发”。用户可以复制内容，理解可能重复执行后自行决定是否重新发送；系统不能用新 ID 隐藏这一风险。“取消等待”或移除本地显示也不能表示撤销了 Pi 中的执行。

## 6. 最小协议与服务端调整

### 一个查询请求，复用一个结果类型

拟新增 `user_message_status_request`，携带现有协议版本、请求 `id`、当前 channel／session／leaf 和原 `client_request_id`。不携带正文、图片或附件原件，不调用 `onUserMessage`、SDK 或入队接口。

结果复用 `user_message_status`，以查询请求的 `in_reply_to` 关联本次查询，以 `client_request_id` 关联原消息。沿用已有 `received`、`accepted`、`committed`、`unknown_delivery`，只补充业务确有需要的结果：

- `rejected`：确定尚未进入可能投递阶段，附受控错误码与是否可重试；不暴露异常正文、路径或消息内容。
- `cancelled`：已确认从可取消队列中移除，不代表停止了已执行消息。
- `not_found`：当前证据中没有记录，仅用于查询结果；不是允许重发的证明。

`accepted` 是否已启动继续结合 `message_id` 与队列快照判断，不再增加一套平行的 wire 状态命名。新增字段和变体在共享包内严格定义，未知字段、非法组合和错误方向继续拒绝。

### 按投递证据合并状态

不为状态枚举设置一个顺序后取最大值，也不采用“最后到达的回执覆盖之前状态”。`received` 只证明 Extension 收到请求；不带 `message_id` 的 `accepted` 可能只是排队；`unknown_delivery` 表示必要阶段尚未确认，不抹去此前已经收到的证据。

合并前先校验目标、连接与请求关联，发送尝试 ID 和查询 ID 分开维护。查询结果须结合查询发起后收到的新证据判断；已失效目标或连接的结果不参与合并。

| 已有或新收到的证据 | 合并规则 |
| --- | --- |
| 已关联正式用户记录 | 原位合并并结束本地投递等待；迟到回执、查询失败或 `not_found` 不复活 pending，也不重新显示投递异常 |
| 已收到 `user_message_started`、带 `message_id` 的 `accepted` 或 `committed` | 保留消息关联和已启动／提交的结论；较早的接收回执、未知、拒绝或查询失败不能回退它。尚未取得正式记录时继续历史补齐，不伪造历史，也不因补齐慢而重发 |
| 只有 `received` 或不带 `message_id` 的 `accepted`，尚无启动证据 | 保留接收事实，排队／在途以完整队列快照为准；真正排队不超时，在途启动超时或去向不明仍可进入“尚未确认”，不能把 `accepted` 一律当作投递完成 |
| 匹配发送尝试的拒绝，或查询确认的拒绝 | 仅在没有较新的受理、启动／提交或可能已投递证据时转为失败；新尝试开始后，旧尝试的拒绝和旧查询结果不能结清新尝试 |
| 已确认取消 | 只结清匹配的未投递队列项；已有启动／提交或正式记录时不能当作取消成功。草稿回填继续遵循仅本端对应撤回请求、仅一次的规则 |
| `unknown_delivery`、`not_found`、查询超时或查询失败 | 不撤销已有的启动／提交或正式记录；仍缺少必要投递证据时保留“尚未确认”，不能仅凭这些结果开放重试发送 |

### 查已有证据，不新建第二份日志

查询先读已有附件投递保护记录：附件消息已提交或可能已投递时直接按该结论答复，保留“可能已投递”的保守结论，不能被普通记录缺失覆盖。其余读有效的会话投递记录，没有记录时再查真实队列；已知正式消息 ID 时核对当前正式投影。

查询必须独立于旧请求的 channel 绑定，答复当前有效查询 channel；不能为了查询而创建幂等记录、重新入队或重置原请求状态。只接受 Relay 注入的 Owner 身份，并校验 runtime、session 和当前 channel，不能查询其他 Owner 的消息。旧连接的结果不能写回新会话。

普通 leaf 前进不应破坏同一消息的关联；真正的分支重置、会话替换和 runtime 更换仍按既有失效边界处理。幂等记录过期、容量回收或进程重启后允许返回 `not_found`，不承诺从全文历史推断或扫描恢复全部消息。

### 失败重试与未知核对严格分开

- 本地编码、准入或传输明确未提交，以及服务端在调用投递前的确定拒绝，可以判失败。
- 一旦已经尝试调用 Pi，SDK 同步抛错也不能直接证明没有执行；附件已标记 `mayHaveDelivered` 时尤其必须保持未知。
- 不把所有 `protocol_error` 一律归成失败；按出错阶段和已掌握的投递证据分类。无法证明未投递时保守处理。
- 明确失败的重试保留逻辑 `client_request_id` 和气泡身份，每次网络尝试生成新的请求 `id`；正文与附件集合保持不变。改内容是新消息，不复用旧 ID。
- 对同 ID 的可重试拒绝，服务端在 payload 指纹一致、目标有效且尚未可能投递时，在该记录的有界尝试预算内，每个未处理过的请求 `id` 允许一次重新准入；先原子切换到受理状态，再执行后续投递。拒绝发生在入队和调用 SDK 之前，重复准入不会重复执行；相同尝试的重复帧只重放结果，不能因中间经过另一个尝试而重新准入。预算耗尽时保留旧尝试的防重复保护，并停止重新准入，返回不可重试的 `unavailable`；上限见[会话协议](../../reference/protocol/protocol-v2.md#消息投递确认)。
- 已接收、排队、启动、提交或结果未知的同 ID 请求仍只重放状态，禁止二次调用 SDK。PWA 删除旧的 `retryUnknown → user_message` 路径，不保留隐藏入口。
- 重试前做在线、目标、附件租约和同步连点门禁；本地再失败立即回到失败态，不留下内部 pending 与界面失败互相矛盾的状态。
- 新请求 ID 与查询 ID 分别关联。迟到的旧拒绝或查询不能覆盖较新的肯定回执；已关联的正式记录是最终依据。

这些约束利用现有有界内存与附件保护，不新增持久化投递日志。明确拒绝和取消的结果在既有预算内保留，便于回执丢失后查询；到期或清理后返回 `not_found`。查询不能借命中记录无限续期，也不能逐出附件仍有效的防重复保护。实现必须覆盖现有记录释放和查询并发，不能靠延长 TTL 声称永久幂等。

## 8. 验收要求

### 必须覆盖的场景

1. 正常文字、附件消息不出现“发送中”；正式回执先到、事件先到都只保留一个气泡，同文连续发送不误合并。
2. 本地准入拒绝保留草稿；已接管后的同步发送失败只有一份消息，原地重试不产生第二条，不清除后续草稿。
3. 远端明确拒绝显示正确原因；可重试拒绝的重复帧、连点和新尝试不会导致重复 SDK 调用。不可重试拒绝没有误导按钮。
4. 服务端已受理但回执丢失，重连查询恢复真实状态；查询次数和 SDK 调用次数分别断言，不能只测试按钮回调。
5. SDK 抛错或启动超时仍为未知；点击核对不会重新发送。`not_found`、查询超时、旧端不支持查询都不能触发补发。旧端用例覆盖真实的 `protocol_upgrade_required` 回执，断言仅处理匹配查询，不重置会话、不叠加同一原因的全局错误。
6. 队列等待超过普通确认超时仍为排队；在途、取消、插入与正式记录乱序时，快照缺席不被误判，草稿最多回填一次。
7. 附件上传成功但消息提交失败、交接时断线、同租约重试、租约变化、可能已投递原件保护均有覆盖；不能重复上传有效文件或误删原件。
8. 旧 Owner／channel／runtime／session 的查询与回执被隔离；普通 leaf 前进不丢关联，真实分支重置不转投消息。
9. 几何验证覆盖桌面、窄屏、大字号与减少动态效果：状态交接不重建气泡、不回弹，不增加永久留白；异常图标可触达、可读屏。若实现“返回草稿”等动作引入叠层，再按项目 overlay 技能验证。
10. 本地历史写入失败不能变成投递失败；刷新不保证恢复未确认内容的边界有明确说明，不用测试夹具冒充跨刷新恢复能力。
11. 查询期间先收到启动／提交回执或正式记录，后收到旧的 `received`、`unknown_delivery`、`not_found` 或拒绝时，已确认结果不回退，已合并气泡不复活 pending；仅有不带 `message_id` 的 `accepted` 后进入在途且启动超时，仍应显示“尚未确认”。

### 实施时的验证层级

- 修改共享协议后先构建共享包，再运行相关严格 schema、编解码和协议 fixture 测试。
- Extension 行为变更执行该包 `verify`，重点包含投递、绑定、队列和附件回放测试。
- PWA 执行类型检查、lint、直接受影响的 Node／Browser Mode 测试及构建；本地不跑无关的整批浏览器组件文件。
- 此项跨共享协议、Extension 与 PWA，集成验收再执行根 `pnpm verify` 和 `pnpm test:e2e`，覆盖真实 Relay 路由与双 Owner 隔离；运行前按项目环境要求检查服务，不自动发布。
- 最终检查实际 diff、`pnpm check:docs` 和 `git diff --check`；本地定向验证不能替代根 `pnpm verify`、`pnpm test:e2e`、旧端联调与真机验收。

## 9. 发布与兼容边界

沿用现有 Protocol v2 外层与严格 schema，不引入 v1 回退或并行协议栈。新增查询与结果只针对本轮配套 PWA／Extension 交付；保持[先部署 PWA、再发布 Extension](../../DEPLOYMENT.md#extension-npm-发布)的项目顺序。

发布窗口里旧 Extension 不识别新增查询时，按核对基线的[解码路径](../../../pi-extension/src/transport/peer_channel.ts)会返回 `protocol_error`，错误码为 `protocol_upgrade_required`，并用 `in_reply_to` 关联查询请求；不能只测试 `unsupported_type`。PWA 校验当前目标、channel 与查询 ID 后，仅将它作为本次查询不可用处理：尚无更强投递证据时保留“尚未确认”，在消息处提示更新 Extension，不触发会话重置、补发或同一原因的全局错误。其他查询失败同样不能证明消息未投递，结果合并遵循 §6。

这只是明确的不可用反馈，不增加旧端查询实现。新增回执形态不承诺旧 PWA 页面可识别，发布说明要求刷新页面，不为长期共存增加双写、双解析或 feature flag。

既有正式历史、附件 metadata 与持久身份不因“不要兼容”而被删除或迁移；它们是仍需读取的数据，不是被替代的执行分支。发布、staging 覆盖、版本变更与生产验收仍需各自授权。
