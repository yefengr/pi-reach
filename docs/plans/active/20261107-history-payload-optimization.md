# 在线会话历史传输体积优化

- 事项入口：[BACKLOG「在线会话历史传输体积优化」](../../BACKLOG.md#在线会话历史传输体积优化)。
- 用途：记录减少在线会话历史传输量、缩短首次打开等待的候选方案，不作为当前实现说明。
- 授权边界：本次只记录方案，尚未确定开发。请求超时与恢复反馈的第一层修复另行实施，不据此授权分页、图片交付或协议变更。
- 当前事实来源：[状态与持久化所有权](../../ARCHITECTURE.md#状态与持久化所有权)、[PWA 活动选择与历史](../../ARCHITECTURE.md#pwa-活动选择与历史)、[会话协议](../../reference/protocol/protocol-v2.md)。

## 为什么需要第二层

避免误报超时与缩短等待是两个目标。按有效分片进度管理超时，可以让较慢但持续推进的历史请求完成；它不会减少必须传输的数据，也不能保证首次打开更快。

在线会话的近期窗口按事件条数选取，但工具结果可能包含图片 Base64。同样数量的事件，实际体积可以相差很大；合法事件经过历史分片及外层 Base64 封装后，传输文本还会进一步增大。因此，仅调整等待期限不能替代体积优化。

### 修复前诊断快照：2026-11-07

以下是 PWA 0.0.38 在桌面 Chromium 中，通过真实 Relay 加载私有会话副本的观测，不是性能目标或当前实现约束，也不代表手机真机结果：

| 项目 | 观测 |
| --- | --- |
| 请求窗口 | 最近 30 条正式记录 |
| 接收文本 | 约 949 万字符，包含 Base64 封装；不等于原图片大小或完整 TLS 流量 |
| 原逻辑 | 请求发出约 15 秒后超时，此后仍有数据到达 |
| 单变量对照 | 仅延长诊断页内存中的等待期限，同一窗口约 22.8 秒完整加载 |

这次对照验证了固定期限与实际传输耗时不匹配，没有进一步定位服务器出口、网络路径和发送节奏各自的耗时，也没有测得故障手机的内存峰值。

## 目标与非目标

目标是减少打开在线 Pi 会话时必须同步的内容，让用户更早看到可用记录，同时保持正式历史、分支和发送语义正确。

本方案不包括：

- 通过删除原会话内容、清空浏览器历史或丢弃图片来制造加载变快的结果。
- 将本地只读历史改成远程恢复或后台补齐；其数据来源仍遵循现有架构。
- 为 Relay 增加内容解析、会话存储、图片缓存或新的 HTTP 下载服务。
- 更改配对、身份、授权、运行结束判定或消息投递确认规则。
- 将工具结果图片直接视为已经具备可回取原件的上传附件。

## 优先评估的路线

### 1. 用字节预算约束一次历史响应

先核对 Extension 历史分页器和 PWA 加载器能否在保持现有游标契约的前提下，按累计体积提前结束一次响应，再继续补齐所需范围。保留条数限制，但不再把条数当作传输量的代理指标。

启动时需确认：

- 预算按事件编码体积、分片解码体积还是外层传输文本计算，如何覆盖编码开销。
- 提前结束响应后，`next_before`、`eos` 与连续序号校验仍然正确，不能跳过或重复正式事件。
- 单个事件超过窗口目标预算时如何前进，不能产生无进展重试。
- 降低单次响应体积是否只是把同一大窗口拆成更多请求，还是确实改善首次可见内容和恢复完成时间。

优先复用现有分页与缺口补齐能力；只有现有契约无法表达时，才提出独立的协议调整及兼容方案。

### 2. 评估工具结果图片的按需交付

评估让常规历史携带必要的图片描述或受控引用，用户查看工具详情时再获取完整内容，而不是每次恢复都搬运大段 Base64。

优先核对现有文件与附件获取机制是否可复用，不新增平行的下载系统。工具结果图片可能只有内联内容，没有稳定文件来源；需要先明确原件保存、作用域、生命周期、完整性和不可用回退，不能假设现有附件原件机制已经覆盖它们。

旧内联历史应继续可读。新旧 PWA、Extension 的组合、Pi 重启、分支切换、原件缺失和离线阅读的行为，需要在实施前单独确认；不能用字段占位或静默丢图代替兼容方案。

### 3. 同时检查冷启动与缓存复用

分别测量首次打开、已有本地缓存、切回会话、断线重连和向前翻页。复用浏览器已有的正式事件与检查点，不建立第二份权威历史，也不因减少传输而削弱分支一致性核对。

## 保持的边界

- 正式事件仍按稳定身份与序号合流；分支替换仍须在必要记录完整校验和持久化后原子提交。
- 只有会话准备完成后才能发送，不把提前显示部分内容等同于发送就绪。
- 本地只读历史不暗中建立 Relay 连接或获取原件。
- Relay 继续只转发外层帧，不解码、记录或持久化 `ct`；当前 `ct` 是 Base64 封装的 JSON，不是应用层端到端加密数据，传输保护依赖 TLS。
- 不把本地路径、凭据、配对码、消息正文或图片 Base64 写入日志、基准报告和测试输出。自动化夹具使用明确标注的隔离合成数据。

## 实施前确认与验收

正式开发前，先冻结字节预算、首屏可用的定义、图片来源与降级行为，以及是否需要共享协议变更；发生协议变更时，遵循项目既有兼容与发布流程。

至少比较以下指标：传输文本与解码字节数、请求和分片数量、首次可见时间、完整恢复时间、浏览器内存峰值及缓存复用情况。性能目标应在第一层修复后的同条件基线上确认，不把上述单次诊断快照作为固定门槛。

验证覆盖纯文本、少量图片、多图片及单个大结果，并包含慢网络、中途停滞、取消、重连、切会话、旧内联历史和原件不可用。自动化之外，需要 iOS／Android 真机补证，桌面移动视口不能代替设备验收。
