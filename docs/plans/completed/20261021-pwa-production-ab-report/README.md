# PWA 生产编译性能 A/B 报告

2026-10-21 · 阶段 1–2 整体优化对照 · 本地受控回放

**这份报告测量浏览器主线程工作量、显示延迟和 JS 堆，不测量手机电量或温升。**

## 结论

- 五个活跃场景的主线程任务占用中位数降低 **33.9%–72.6%**，每个场景四对结果都同向。普通 60 条历史降低 **70.1%**，300 条历史降低 **68.8%**。这支持阶段 1–2 整体优化在本实验中有效，不能据此换算省电或降温百分比。
- 降低工作量没有靠整体推迟正文显示：300 条历史的计划输入→DOM p95 从 **5912.7ms 降至 151.5ms**；正式接管前已显示的完整序号从 **14/120 提升到 120/120**。短会话 p95 约 **150ms → 150ms**，没有同量级延迟退化。
- **长回复仍然慢。** 约 24KiB 初始 Markdown、累计 blocks 回放的显示 p95 仍有 **800.7ms**，长任务中位数仍为 **16 次**。其活动期 Task 仅从 **6474.3ms 降至 6156.8ms**（约 4.9%），总量的较大改善主要体现在完成尾部；不能把总降幅 33.9% 解读成持续解析也快了三分之一。
- 没有统一的“所有指标变好”结论：短会话相邻推进间隔 p95 **53.0ms → 69.5ms**，更新节奏更成批；300 条历史的 Layout/Style 时长上升，同时实际显示推进更多。GC 后堆略低，但部分场景的本轮新增堆更高，**不宣称已解决内存或泄漏问题**。
- 5 秒空闲样本只有约 **7–8ms** 主线程任务占用、无长任务，前后相对波动不一致。这不是待机功耗测试，也不足以证明不存在更长周期后台活动。

## 测了什么

两版使用真实 PwaApp、Provider、页面壳、历史加载、消息接收后的运行态处理、渲染、输入区和 IndexedDB。通过正常分页把指定历史全部加载到 DOM 和本地存储，再开始回放；工具场景打开真实工具阅读器。

为了固定输入，生产编译时替换启动入口和 RelayClient/PeerChannel 传输，跳过 Service Worker 注册；所有输入均为合成数据，外部网络被阻断。因此这是**同业务代码的隔离生产编译**，不是原样线上镜像。它不覆盖真实模型、Relay、加密编解码、网络耗时、Service Worker、冷启动或安装体验。

“Task”指 CDP TaskDuration 的主线程任务占用时长，是工作量代理，不是 OS 精确线程 CPU 时间；任务内阻塞、系统调度和共同探针均可能影响它。正文显示以 DOM 提交为代理，不等于屏幕像素呈现。

## 完整性、统计与边界

- 全部正式样本通过：实际历史条数、所有 partial 的计数和输入指纹、最终正文逐字符一致、run_end 落盘、最终 DOM 序号 1..N 完整有序、正式结束前存在流式推进、无回退、无浏览器或外网错误。共用夹具不是把最终答案直接注入内部显示 hook。
- 输入由独立 Worker 按绝对时刻发送，主线程忙时仍能记录排队差异；同时保留计划、Worker 发送、主线程接收、DOM 提交和下一 rAF 时刻。合并更新时用后续完整前缀计算覆盖延迟，不把被合并帧记成零延迟。
- 每场景按 AB、BA、AB、BA 跑四对，全新 context，顺序执行。总 Task 在正式正文和结束事件保存完成、DOM 静置后才结束，另采正式注入前边界，分开活动期与完成尾部。尾部真实处理和少量保存门禁读开销均保留，不把空等墙钟当 CPU 工作。
- 表中为四轮中位数；延迟先逐轮计算 p95，再对四轮聚合。相邻推进间隔不包含“计量开始→首次推进”等待。仅四次重复，不宣称统计显著性；不把相关帧当大量独立实验。
- 正式采样只有一次完整尝试，48/48 有效，无删除、补样或筛除。准备期发现过入口替换过晚、500ms 尾窗未等到保存完成的问题，均在正式采样前修正；相关失败及后续带时间尝试列于索引。早期部分成功试跑被后续试跑覆盖，未进入任何正式统计。
- 内存是窗口末值和强制 GC 后参考，不是峰值、整机 RAM 或泄漏测试。CPU 也包含 JSON 指纹、DOM 观察、一次 CDP 边界和结束门禁等共同探针开销，没有声称扣除；边界往返可能把少量待处理工作分到尾部，总量不受该分段归类影响。
- 没有控制整机热状态或排除所有系统服务；未并行运行其他主动浏览器测试/构建，但 JIT、GC、缓存和系统噪声仍存在。桌面原生 CPU、移动尺寸窗口不能代表手机 Safari/Chrome 或安装 PWA。
- 20Hz/50Hz 是人为固定输入，不是线上负载分布的抽样，不能把表中百分比当作所有日常使用场景的收益。Composer 被挂载，但本轮没有模拟输入、滚动、菜单/附件或前后台切换，不为这些行为额外背书。
- 本次把阶段 1–2 作为整体比较，不能分配单项优化贡献；也不能把旧开发模式组件微基准与本报告的整页生产编译累计指标直接比较。

## 下一步应做什么

**先剖析长回复/累计 blocks 路径，而不是立即虚拟化。** 在相同 60 条历史下，长回复的优化后 Task 为 6584.6ms，普通回复为 1954.9ms；它仍有 16 次长任务和约 801ms 显示 p95，是本轮最明确的残余压力场景。

下一轮适合对这个固定回放抓生产 trace，区分增长正文的 Markdown 解析、累计 blocks 处理、React 提交与完成尾部，再按证据选择局部增量处理或缓存。当前数据还不能把开销归因到单个函数，也没有证据要求先承担动态高度虚拟列表的回归风险。启动拆包不在本次运行期回放覆盖内。

如果目标仍是“手机不发热”，则需补充具体设备、系统、浏览器/安装 PWA 模式，使用平台支持的真机性能或能耗工具重复固定负载；不要再以手摸温度作为本轮优化的验收证据。本次没有改变业务代码、提交、推送或部署。
