# 会话附件上传方案

本文记录会话附件的产品边界与实施验收。本轮已按用户确认的“本地实现与验收完成”范围结束：正式实现、相关自动化、独立审查和真实 Relay 链路已收口。真机、真实缓存升级等未覆盖项保留为发布前检查，不标记为通过。本轮不包含提交、推送、发布或部署。

当前架构与公开协议分别以 [ARCHITECTURE](../../ARCHITECTURE.md) 和[协议与安全总览](../../reference/protocol/README.md)为准。本文不独立维护项目级状态；事项状态由 [ROADMAP](../../ROADMAP.md) 维护。

## 目标与现状

目标是让用户从 PWA 把文件交给当前 Pi 会话处理。文件先经 Relay 传到电脑，由 Extension 保存；全部附件准备完成后，再把文字、附件清单和本地路径交给 Pi。文件不再局限于图片，也不要求与聊天正文共享单条消息的容量预算。

这不是通用文件传输或文件管理器。第一版不提供任意保存位置、目录浏览、原件下载、文件管理界面或离线投递，也不新增电脑 HTTP 上传服务、NAT 穿透或常驻后台进程。只有当前在线且加载 Extension 的 Pi 能接收上传，沿用[纯 Extension 运行时决策](../../adr/20260914-pure-extension-runtime.md)。

以下为方案访谈时的实施前快照，不代表本轮修改后的实现：

| 实施前事实 | 代码与文档依据 |
| --- | --- |
| PWA 将图片在浏览器内缩放、重新编码为 PNG 或 JPEG，再生成 Base64；图片与文本共同受内层帧大小限制 | [`prepareImageAttachment`](../../../pwa/src/lib/pwa/image-upload.ts) |
| `user_message.images` 最多一张；尚无本方案的通用附件上传流程 | [`userMessageFrameSchema`](../../../packages/protocol/src/session/frames.ts)、[协议总览](../../reference/protocol/README.md#timeline-与附件) |
| PWA 将内层消息编码后放入 `route.ct`，通过既有 Relay 连接发送 | [`PeerChannel.send`](../../../pwa/src/lib/pi-reach/peer-channel.ts) |

## 已确认的产品决策

下表是本方案产品边界的集中记录。后续章节解释流程和验收，不另设相互独立的默认值。

| 编号 | 决策 | 边界与取舍 |
| --- | --- | --- |
| 1 | 做当前 Pi 会话的附件 | 不承诺独立于会话的文件管理或任意电脑目录传输 |
| 2 | 已发送附件长期保留 | 不因任务结束、Pi 退出、电脑重启或时间到期而自动删除；不做主动清理功能 |
| 3 | 存放在 Pi Reach 专用目录 | 使用 `~/.pi/pi-reach/attachments/`，按会话隔离，不默认写入项目；目录与随机命名规则见[当前架构](../../ARCHITECTURE.md#会话附件) |
| 4 | 点击发送才上传 | 选择、预览和移除尚未上传的附件仅发生在浏览器；全部上传成功后才提交消息，失败保留草稿，不先发缺少附件的消息 |
| 5 | 所有格式统一提供本地路径 | 图片也不自动注入模型视觉输入；Pi 收到附件清单和路径后，由 Agent 按需调用工具读取 |
| 6 | 一条消息支持多个附件 | 多文件作为同一批材料交给 Pi，不因其中一个先上传成功就先触发处理 |
| 7 | 不设置文件格式白名单 | 保留原件；上传流程只接收和保存，不自动解析、解压或执行；允许上传不等于具备内容理解能力 |
| 8 | 限制单次附件规模 | 单文件最多 **50 MiB**，单条消息附件原件合计最多 **100 MiB**，最多 **10 个附件**；这是产品限制，不是提高协议单帧上限 |
| 9 | 可以回收废弃上传的临时数据 | 明确取消或废弃的上传可以删除其临时数据；这不构成对已发送附件的自动清理授权 |
| 10 | 支持限定范围的断点续传 | 当前页面未刷新、目标 Pi 进程未退出时，短暂断线后从电脑确认的位置继续；不承诺跨浏览器重启、跨 Pi 重启续传 |
| 11 | 切换目标前确认取消 | 上传期间切换 Pi 或会话，先确认取消本次发送；不后台投递、不转投新目标。目标自行退出或切换会话时，旧发送意图失效 |
| 12 | 不设累计存储配额 | 不设置电脑端附件总容量上限，只做磁盘剩余空间保护；空间不足时拒绝新上传，不删除已有附件 |
| 13 | 第一版不支持原件下载 | PWA 展示附件信息，不提供从电脑取回原文件的下载入口 |
| 14 | 图片保留有界缩略图 | 缩略图用于界面，随正式历史保存在浏览器；预览失败退回文件卡片，不阻止原件上传，也不自动成为模型输入 |
| 15 | 允许只发附件 | 不要求附带文字；附件清单只表达文件位置和元信息，不替用户补充“分析”“解压”“执行”等任务指令 |
| 16 | 旧 Extension 禁用新附件发送 | 新 PWA 提示升级，不回退旧图片内嵌发送；文字聊天和已有图片历史继续可用。发布顺序仍为先 PWA、后 Extension |

`MiB` 使用二进制单位，即 `1024 × 1024` 字节。缩略图是独立的展示派生数据，不替换、压缩或修改电脑保存的原件；技术契约限制为 JPEG、最多 320 × 320 像素及 32 KiB。

### 已确认的输入区与逐文件取消

附件区在输入框外、输入框上方，桌面横排换行、手机纵排。卡片约 58px 高，操作点击域至少 44 × 44px。不显示总进度：上传中显示逐文件进度，成功只保留 ✓，失败显示短原因且移除进度条。发送级提示在附件区上方、与输入框左边缘对齐，无提示时不占位；输入框保留自身边框，不加消息区与输入区分隔线。

逐文件 × 停止并移除该文件，其他文件继续上传。用户最终保留的附件全部就绪后自动提交；失败但未移除的附件仍阻止提交。全部附件移除时，有文字则发送文字，无文字则不发送空消息。整次发送因确认切换而取消时，保留原目标草稿，但不自动发送文字，也不转投新目标。

## 从选择文件到提交消息

```text
PWA 选择文件，保留本地待发送附件
  ↓ 用户点击发送
核对目标会话、文件数量与容量，建立本次发送意图
  ↓
通过既有 Relay 路由分片上传
  ↓
Extension 校验并保存完整原件，确认附件可用
  ↓ 用户最终保留的附件均可用，且发送目标仍有效
PWA 提交文字与附件引用
  ↓
Extension 校验引用归属，生成附件清单和受控本地路径
  ↓
调用 Pi 现有消息投递能力，由 Agent 按需读取文件
```

### 本地准备与上传

用户选择文件不立即产生电脑端写入。PWA 应展示本次所选附件，并在上传阶段展示逐文件进度和失败状态，允许取消。可安全解码的常见图片生成小预览；预览不可用时按普通文件展示。

上传与消息提交是两个阶段。电脑收到部分文件、某个文件传输完成或整批文件上传完成，都不等于 Pi 已收到用户消息。不能因为附件已落盘就提前启动 Agent，也不能在一个附件失败时静默降级为仅文字或部分附件发送。

PWA 使用由电脑确认的附件引用，Extension 再解析出真实路径。浏览器不得通过文件名或请求字段指定任意电脑写入位置。附件 ID、元信息、上传回执与消息引用遵循[会话附件协议](../../reference/protocol/protocol-v2.md#会话附件)。

### 交给 Pi 的内容

Pi 接收用户文字以及附件清单、本地路径。图片与其他格式采用同一语义，不再由上传流程自动构造图片内容块；图片上传入口因此不以当前模型是否支持视觉为前提。

仅发送附件时，不额外推断用户想执行什么。Agent 可以依据已有上下文读取材料；缺少明确任务时，可以追问。上传流程不自动执行文件，并不等于为 Pi 后续工具调用新增沙箱或审批机制；工具使用仍遵循 Pi 现有能力与用户指令。

文件路径本身不是文件内容。文本、代码、PDF、Office 文档、图片及其他二进制文件能否被理解，取决于工具和模型能力，本方案不提供统一格式转换服务。

### 断线、重试与目标变化

短暂断线后，PWA 必须以电脑确认的接收进度为准，核对上传标识、归属与续传位置，不能仅根据浏览器已发送的字节数推算完成度。同一批已上传成功的文件不因另一个文件重试而重复上传。

续传只覆盖同一页面、同一目标 Pi 进程仍存续的情况。刷新页面或 Pi 退出后，不承诺恢复原上传，也不自动把旧请求绑定到新 runtime。确定废弃的临时原件按[当前存储生命周期](../../ARCHITECTURE.md#会话附件)回收；可能已交给 Pi 的原件保守保留。

用户切换 Pi 或会话时，先提示切换将取消本次发送；确认后停止原发送，不再向原会话提交，也不转投新会话。进入设置页或短暂断网不等同于切换目标。目标自行退出或切换会话时，即使上传稍后返回成功，也不能继续提交旧发送意图。

当前 `leaf_id` 会随普通消息追加推进，不能简单把每次 leaf 变化当成用户切换会话。上传租约区分普通 leaf 推进与真正 branch reset，且不随临时 channel 重建而更换；归属与失效条件见[会话附件协议](../../reference/protocol/protocol-v2.md#会话附件)。

消息回执丢失不等于消息未投递，也不等于附件已废弃。重试须沿用现有投递关联能力并补齐附件引用的幂等边界，避免重复触发 Agent 或误删可能已被消息引用的文件。

## 存储、历史与可用性

### 电脑端原件

原件放在 Pi Reach 专用附件目录，按会话隔离。已发送附件长期保留，不跟随任务、进程或电脑重启自动删除。文件只有在用户要求将其正式纳入项目时，才由 Pi 按指令复制到相应位置；上传本身不写入项目。

不设置累计存储配额意味着磁盘占用会持续增长。接收端仍需在接收前检查可用空间，并处理上传过程中磁盘写满、权限错误和写入失败。空间保护不得以删除历史附件作为腾出容量的手段。

未完成上传使用的临时数据不是正式附件。明确取消或废弃后允许回收，但不能把短暂断线、尚未收到消息回执或存在重试可能的文件直接认定为垃圾。取消、租约失效与可能已投递时的处理以[当前存储生命周期](../../ARCHITECTURE.md#会话附件)为准。

### PWA 历史

正式历史记录附件名称、类型、大小等元信息；图片另外记录有界缩略图。已经保存到 IndexedDB 的附件信息和缩略图在电脑离线时仍可查看，完整原件不默认复制进浏览器历史。

第一版没有原件下载入口。若手机本地原文件丢失，不能通过 PWA 从电脑取回；用户需在电脑上获取。复制或备份项目目录不会自动包含专用附件目录，电脑迁移和会话备份需同时考虑原件及其路径关系，本方案不承诺跨电脑路径自动修复。

已有内嵌图片历史保持可读，不要求回写或迁移旧事件。新附件的描述、预览和正式消息关联使用 Pi 原生 custom entries，随时间线同步到其他授权浏览器并持久化，不只保存在发送端的临时组件状态。

新附件不自动注入视觉内容，并不消除后续工具结果里的图片数据。Agent 读取图片后产生的工具输出仍属于现有时间线链路；本方案不擅自改写工具输出、截图或旧图片历史的传输规则。

## 安全与传输底线

以下是实现必须满足的正确性要求，不是另行扩展的产品功能：

- 复用现有配对、身份认证和 ACL。Extension 只信任 Relay 注入的 `source_owner_id`；上传、续传、取消和消息引用都要验证归属，不能因附件 ID 可猜测或位于同一电脑就允许操作。
- 客户端提供的文件名、扩展名、MIME 和长度都是待校验数据。文件名用于展示，不作为可任意拼接的落盘路径；防止路径穿越、覆盖已有文件和通过符号链接逃逸专用目录。具体落盘命名与打开方式见[当前架构](../../ARCHITECTURE.md#会话附件)。
- 接收端校验实际字节数、分片边界和最终完整性，不能仅凭客户端宣称的大小标记成功。原件未完整可用前，不允许作为附件交给 Pi。
- 消息提交前再次核对全部引用和发送目标；上传成功回调不能绕过已取消或已失效的发送意图。取消与消息投递发生竞争时，不能虚报“未发送”。
- 使用受控并发、接收缓存和背压；多个 Pi 共用同一磁盘时，空间检查须考虑并发写入，不能只在单进程开始时检查一次。
- Relay 继续只转发，不解码、记录或持久化 `ct`，不建立文件缓存和离线上传队列；不为支持大文件无界放大单帧或连接积压预算。
- 沿用 TLS 和现有身份认证，不新增应用层端到端加密。Base64 不是加密，Relay 运营方仍有读取内容的技术能力；安全边界见[已关闭决策](../../adr/20260518-closed-decisions.md)。
- 日志和错误不能输出文件正文、完整 `ct`、凭据或不必要的本地路径。缩略图属于文件内容，也需要遵守附件可见性和隐私边界。

分片主要用于控制单帧尺寸、内存和重试成本，并不自动降低编码开销。实现沿用 Base64 route 信封，编码膨胀仍然存在；没有引入独立二进制传输通道。

## 兼容与发布

新 PWA 连接不具备附件上传能力的 Extension 时，禁用附件发送并提示升级；文字聊天继续可用，不能通过发送未知上传帧来试探能力，也不回退旧图片发送路径。

实现保留 strict schema 和既有握手结构，使用独立能力查询；仅在得到支持响应后发送上传帧。旧端不认识能力查询时，新 PWA 禁用附件，不回退旧图片发送。旧 PWA 可以读取规范化消息与合法 custom，但不认识新定向帧时仍会拒绝，可能提示协议或会话状态错误。旧页面实测需刷新后重新确认当前会话再发送文字，不能承诺滚动升级期间无可见影响；具体兼容边界见[会话附件协议](../../reference/protocol/protocol-v2.md#会话附件)。

发布遵循[现有部署规则](../../DEPLOYMENT.md#extension-npm-发布)，先部署支持新协议的 PWA，再发布 Extension；每一步仍需单独授权。已有图片历史的读取能力必须保留，不能通过删除旧图片解码或渲染消费者来实现“禁用旧发送”。

## 验收矩阵

下表保留原定完整验收要求。本轮交付按用户确认的本地实现范围结束；已取得的证据与发布前未覆盖项分别列于后文，局部测试不替代跨版本及设备验证。

| 场景 | 必须证明的结果 |
| --- | --- |
| 任意格式与原件保留 | 图片、文本及二进制文件均可上传；落盘原件与输入一致；异常文件名不能逃逸目录或覆盖其他文件；上传本身不触发解析或执行 |
| 单次限制 | 覆盖单文件、总大小与数量的上限和超限边界；PWA 与接收端均不能绕过限制；仍遵守现有单帧预算 |
| 消息提交 | 多附件全部可用才提交一次消息；失败不发送残缺消息；只发附件可用；图片只提供路径，不自动注入视觉内容 |
| 短暂断线 | 同一页面、同一 Pi 进程内可从确认位置续传；不会把重传分片重复写入；已成功文件不因其他文件失败重复上传 |
| 超出续传范围 | 页面刷新、Pi 退出或 runtime 替换后不错误续接旧上传，不自动向新目标发送；给出可理解的失败或重试状态 |
| 目标切换与取消 | 用户确认取消后才能切换；设置页不误触发取消；目标自行变化时旧回调无效；覆盖取消、上传完成和消息提交的竞争 |
| 空间与临时数据 | 空间不足、写满、权限错误和并发写入得到受控处理；明确废弃的临时数据可回收；已发送或投递状态未明的附件不被误删 |
